# Design: The Pipeline Resolves a Module's DAL and Never Applies It

- **Feature ID**: TECH-067
- **Epic**: Topic 07 (Technical Debt)
- **Status**: STUB — not yet run through the `specweaver-design` skill
- **Origin**: found 2026-08-19 closing `TECH-041`, which set out to prove the code-level DAL override
  end to end and had to measure which path implements it first.

## Problem Statement

`C-VAL-03` claims a module's DAL injects stricter constraints into validation. `TECH-041` proved that
on the `sw check --level code` path: the same module passes under `DAL_E` and fails under `DAL_A`.

**On the pipeline path — the one `sw implement` runs — the DAL is resolved, carried, and dropped one
call short of use.**

`PipelineRunner.__init__` calls `seed_dal_level(context)`, which resolves the module's DAL and stores
it on `context.isolation.dal_level`. `test_runner_dal_injection.py` proves that at integration tier,
asserting `DAL_A` / `DAL_D` and `is_strict`. Then `ValidateCodeHandler._run_validation` calls
`execute_validation_flow(...)` with `project_root` and `context`, and **without `dal_level`**.

Measured 2026-08-19 across every caller of that entry point:

| Caller | Passes `dal_level`? |
|---|---|
| `assurance/validation/interfaces/cli.py` (`sw check`) | yes — becomes `effective_strict`, which moves the exit code |
| `interfaces/api/v1/validation.py` | yes |
| `core/flow/handlers/validation.py` (the pipeline handler) | **no** |

So code generated by `sw implement` is validated at the packaged default strictness whatever its
`context.yaml` declares. A module marked `DAL_A` is generated and checked exactly like one marked
`DAL_E`.

## Why this was not simply fixed while it was found

Forwarding the value today would be **inert**, and shipping inert wiring is the substitution
`TECH-041` exists to correct. `dal_level` reaches `_hydrate_architecture` and then the QA atom's
`run_architecture` intent, and **no runner branches on it** — `PythonQARunner.run_architecture_check`
logs it and nothing more. A test written against the forwarded value could only assert that a
parameter arrived, which proves the call, not the constraint.

The `sw check` path does not have this problem because its strictness is applied at the summary
(`effective_strict` turns WARNs into a failure), not inside a runner.

## Candidate Approaches (not yet designed)

1. **Apply strictness at the handler's verdict, mirroring the CLI.** `_validation_output` decides
   pass/fail for the step; give it the same `is_strict` treatment `_print_summary` has, so a WARN
   under a strict DAL fails the step. Small, and it makes the two paths agree — which is the
   argument for it and also the question, since a pipeline step failing is not the same event as a
   CLI exiting 1.
2. **Make runners honour the DAL.** Push strictness down so a `DAL_A` module gets stricter thresholds
   (coverage, complexity) rather than the same findings judged harder. Larger, and it is the reading
   of *"injects stricter constraints"* that matches the words most closely.
3. **Descope it to the CLI.** Say the code-level DAL override is a `sw check` feature, delete the
   `dal_level` seeding from the pipeline path so nothing carries a value it never uses, and record
   that generated code is validated at default strictness.

**The decision is what strictness should mean for generated code**, and 1 and 2 answer it
differently: 1 judges the same findings harder, 2 produces different findings. They are not
increments of each other.

## Non-Goals (proposed, pending design)

- The `sw check` path. Proven by `TECH-041`, unchanged.
- The spec-level DAL path. Proven twice, unchanged.
- Making runners branch on DAL for *architecture* specifically — that is `B-SENS-07`'s territory
  where Kotlin and Rust are concerned, and `TECH-064` has already made their silence legible.
- Removing `seed_dal_level` from the runner. It also feeds isolation decisions, which do consume it.

## Next Step

Run `specweaver-design`. Take the scope decision first — 1, 2 or 3 — because the test that proves it
differs in each case, and writing the wiring before the decision is how the value came to be carried
and unused in the first place.
